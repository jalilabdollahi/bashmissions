Think of the script as a pipeline of gates followed by a loop. The gates run in an order that matters: a freeze or a held lock must stop you before you pull or change anything; the pull must succeed before you read the manifests; the manifests must all be valid before you touch a single application; and the plan must fit the change budget before you start. Only then do you loop over the applications. Inside the loop, every change has the same three beats: apply, check health, then either record success or undo. Compute the whole plan first (what is created, updated, unchanged, orphaned) and keep it in arrays, so dry-run, the budget check and the real run all use the same facts.
