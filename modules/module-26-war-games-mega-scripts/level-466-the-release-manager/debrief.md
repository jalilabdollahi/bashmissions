# Debrief: The Release Manager

Releasing is mostly about **order and honesty**. The order: do everything that can fail and be
undone first, then the one thing that cannot, then the optional extras. The script builds the
tarball and a changelog *beside* the old one, tags last, and only then replaces the
changelog; if the tag fails, one `rm -f` returns the directory to where it started. A failed chat
announcement, on the other hand, is reported but never rolls back a release that is already
real: not every failure deserves the same response, and deciding that deliberately is
part of the design.

The honesty: the version is computed from what the commits *say* they did. Semantic
versioning is only a useful promise if the number follows the change, and a machine that reads
`feat!:` is stricter than a person at the end of a long shift. Capturing the pieces with a regex
and `BASH_REMATCH` is the Bash idiom for this sort of light parsing, and `local -n` name
references let one function render any of the lists.

Notice also what the dry run does for you: the preview is generated by the very same
function as the real thing, so it cannot drift from reality.

Going further: next up is a watchdog for something that expires on a schedule nobody remembers:
TLS certificates.
